# AI 应用开发面试要点(RAG / FastAPI / Docker 方向)

## 1. 什么是 RAG,为什么需要它

RAG 是"检索增强生成"(Retrieval-Augmented Generation)。大模型本身只见过公开训练数据,
并不知道企业内部的文档、产品手册或业务规则,直接提问要么答不上来,要么一本正经地编造。
RAG 的思路是:先从自有知识库里检索出与问题最相关的若干片段,再把这些片段作为参考资料一起交给模型,
要求它只依据资料作答。这样带来三个好处:一是让模型能回答私有知识;二是答案可以标注引用来源,
便于人工核对;三是大幅降低幻觉,因为模型的作答被约束在了给定资料范围内。

## 2. RAG 的完整链路

一条完整的 RAG 链路包含五个环节:
1) 文档解析:把 PDF、Markdown、Word 等格式统一转成纯文本;
2) 文本切分:把长文档切成若干语义相对完整的片段,片段之间保留重叠;
3) 向量化:把每个片段转成向量,并建立可检索的索引;
4) 检索:把用户问题也转成向量,与库中向量计算相似度,取分数最高的 Top-K 个片段;
5) 生成:把命中的片段编号后填入提示词,要求模型依据资料回答并标注引用编号。
工程上还需要考虑索引持久化、增量更新、召回质量评估等环节。

## 3. 文本切分策略与重叠的作用

切分粒度直接决定召回质量。粒度太大,一个片段里混了多个主题,检索出来的噪声多;
粒度太小,答案被切碎,模型看不到完整上下文。
实践中不做简单的定长切片,而是先按空行和标题切段落,再把段落按顺序装进不超过 chunk_size 的块,
超长段落才硬切。片段之间保留 chunk_overlap 长度的重叠,是为了避免关键信息正好落在切口上,
导致上下两半都召回不到完整语义。重叠也不能太大,否则索引冗余、检索结果高度雷同。

## 4. 稀疏向量与稠密向量的区别

稀疏向量(如 TF-IDF、BM25)以词为维度,只有出现过的词才有非零值,靠字面匹配打分,
优点是无需训练、可解释、离线可用,缺点是近义词、改写句召回不了。
稠密向量(如 BGE、text-embedding 系列)把文本映射到几百上千维的语义空间,
靠语义相似度打分,能召回"表述不同但意思相同"的内容,缺点是需要额外的模型服务或推理开销。
工业界的常见做法是混合检索:两路各自召回,再融合排序,兼顾字面命中与语义泛化。

## 5. 相似度阈值的作用与调参

余弦相似度给出的是相对分数,不同向量化后端、不同语料的分布差异很大,
因此不能直接拿 Top-1 结果就用。做法是设一个 score_threshold,低于该分数的片段直接丢弃,
这样"知识库里根本没有相关内容"的提问就不会硬塞一段无关文本给模型。
阈值需要实测确定:先分别测一批相关问题和无关问题的分数分布,
把阈值放在两者之间的空隙里,既能保证召回,又能过滤噪声。
向量维度也会影响分布,维度提高可以减少哈希冲突,让相关与无关问题的分数差距更明显。

## 6. 如何防止大模型幻觉

三道防线。第一道是检索层的阈值过滤,把明显不相关的片段挡在外面;
第二道是提示词约束,明确要求"只依据下方参考资料作答,不要使用资料之外的信息,
资料不足以回答时直接说明无法回答",并要求标注引用编号;
第三道是产品层设计,答案附上引用来源供人工核对,同时对关键业务场景保留人工兜底。
要注意的是,只靠提示词不足以完全消除幻觉,检索质量才是根本 —— 垃圾进,垃圾出。

## 7. 向量库选型:什么时候需要 FAISS 或 Milvus

语料在几千个片段以内时,把向量存成矩阵、用矩阵点积做全量比对就够了,
一次查询的耗时可忽略,完全没有必要引入外部服务。
真正需要专业向量库的信号有三个:数据量到十万级以上、要求毫秒级响应、
或者需要多租户隔离与增量更新。此时可以换 FAISS(单机高性能)、Milvus 或 Qdrant(分布式)。
关键在于抽象出统一的存储接口(增、删、查、持久化),让检索层不感知底层实现,
将来替换时上层业务代码不需要改动。

## 8. 流式输出与 SSE

大模型生成一段几百字的回答往往要几秒钟,如果等全部生成完再一次性返回,
用户会盯着空白页面等待,体感很差。
流式输出是把模型返回的增量文本块立刻推给前端,边生成边显示,首字响应时间通常不到一秒。
Web 端常用 SSE(Server-Sent Events)实现:服务端保持一个长连接,
每个事件以 data: 开头推送一段 JSON,前端逐条解析并追加到界面上。
相比 WebSocket,SSE 是单向的、基于普通 HTTP,实现和调试都更简单,
而且天然兼容 Nginx 反代与浏览器自动重连,适合"服务端持续推送、客户端不需要回推"的场景。

## 9. FastAPI 的核心优势

FastAPI 基于 Starlette 与 Pydantic。它最大的优势是用类型注解同时完成三件事:
请求参数校验、数据序列化、接口文档生成。定义一个带类型的 Pydantic 模型,
框架就会自动校验入参、返回结构化错误信息,并生成可交互的 Swagger 文档,
不需要再手写接口文档或参数校验代码。
原生支持 async/await,在等待大模型响应这类 IO 密集场景下能显著提高并发能力。
依赖注入机制则让数据库连接、配置、服务对象等资源的管理更清晰,也方便测试时替换实现。

## 10. 前后端分离的收益

把界面与能力拆成两个服务,收益有四点:
一是能力复用,同一套接口可以同时服务网页、移动端和其他后端服务;
二是可调试性,接口层自带文档,可以直接用 curl 或 Postman 验证,不必通过界面;
三是可独立部署与扩容,模型推理慢时可以只扩后端实例;
四是职责清晰,前端专注于交互与展示,后端专注于业务与模型调用,便于分工与测试。
代价是增加了一层网络调用,需要处理跨域、超时与错误传递。

## 11. Docker 解决的问题与镜像分层

Docker 解决的是"在我机器上能跑"的问题:把代码、运行时、系统依赖打包成镜像,
在任何装了 Docker 的机器上结果一致,彻底消除环境差异。
镜像由多条只读层叠加而成,每条 Dockerfile 指令生成一层,层会被缓存复用。
因此 Dockerfile 的编写顺序很关键:先复制 requirements.txt 并安装依赖,
再复制业务代码。这样只要依赖没变,改代码时重建镜像可以直接命中缓存,构建时间从几分钟降到几秒。

## 12. 容器为什么用非 root 用户运行

容器默认以 root 运行,一旦应用存在漏洞被利用,攻击者拿到的就是容器内的 root 权限。
如果容器还挂载了宿主目录或与其他容器共享命名空间,风险会进一步扩大。
正确做法是在 Dockerfile 中创建普通用户,用 USER 指令切换到该用户,
并只授予必要的目录权限(例如应用的数据目录)。
这属于最小权限原则的落地,成本极低但能显著缩小攻击面,是容器安全的基线要求。

## 13. 大模型调用失败的常见原因与处理

常见失败分四类:认证类(API Key 无效或未配置,返回 401)、额度类(余额不足或超配额,返回 402)、
限流类(请求过于频繁,返回 429)、网络类(超时、连接失败、代理异常)。
工程上不应该把底层异常直接抛给用户,而要统一翻译成可读提示,并区分是否值得重试:
限流和超时可提示稍后重试,认证和额度问题必须让用户去改配置或充值。
另外要做好兜底:用户提问先落库再发起模型调用,这样即使调用失败,输入内容也不会丢失,
前端可以基于保留的消息提供"重新生成"入口。

## 14. 上下文窗口管理与 token 控制

多轮对话会把全部历史都发给模型,轮数一多就会超出上下文窗口,而且 token 消耗与费用线性增长。
常用做法是滑动窗口:只保留最近 N 轮对话,
并在截断后修正起始角色,避免出现"以助手消息开头"的畸形上下文。
更进一步的方案是做历史摘要,把早期对话压缩成一段摘要长期保留,
在不丢失关键信息的前提下控制长度。检索增强在某种程度上也缓解了这个问题:
知识不必全塞进上下文,需要时再检索出来。

## 15. 会话持久化的原子写入

会话数据直接写目标文件存在风险:如果写入过程中进程被中断或磁盘出错,
文件会处于写了一半的状态,下次读取直接解析失败,用户的历史记录就永久损坏了。
解决办法是原子写入:先把完整内容写到一个临时文件,
确认写成功后用重命名操作替换目标文件。
同一文件系统内的重命名是原子操作,要么完全成功,要么完全不变,不存在中间态。
读取时对解析失败做兜底处理(返回空会话而不是崩溃),可以进一步提升健壮性。
